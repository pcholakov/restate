================================================================================
        DISTRIBUTED SNAPSHOT WALKTHROUGH: TWO PARTITION PROCESSORS
================================================================================

SEE ALSO: pitr-snapshot-design.md - High-level design and rationale

This document walks through a concrete example of how two partition processors
(P0 and P1) coordinate to take a consistent distributed snapshot using a
modified Chandy-Lamport algorithm with markers and acks flowing through Bifrost.

NOTE: This walkthrough is limited to the two-partition case for clarity. The
N-partition case follows the same principles but requires tracking markers from
all N-1 other partitions.


================================================================================
CHANNEL MODEL: WHAT CHANNELS EXIST?
================================================================================

Each Partition Processor (PP) participates in multiple communication channels:

1. CROSS-PARTITION CHANNELS (Pi → Pj, where i ≠ j)
   ────────────────────────────────────────────────
   Messages from Pi to Pj flow through Log-Pj via the shuffle mechanism.
   These are the primary focus of Chandy-Lamport.

2. SELF-LOOP CHANNEL (Pi → Log-Pi → Pi)
   ─────────────────────────────────────
   Each PP also writes commands to its OWN log, which are then applied:

   ┌─────────────────────────────────────────────────────────────┐
   │                    Partition Processor Pi                    │
   │  ┌─────────────┐                      ┌─────────────┐       │
   │  │ State Machine│ ──[propose]─────────│ SelfProposer│───────┼──> Log-Pi
   │  └─────────────┘                      └─────────────┘       │
   │        ↑                                                     │
   │        │ apply                                               │
   │  ┌─────────────┐                                            │
   │  │   Applier   │ <────────────[read]────────────────────────┼─── Log-Pi
   │  └─────────────┘                                            │
   └─────────────────────────────────────────────────────────────┘

   This self-loop IS a channel in CL terms: commands generated by the state
   machine travel through Bifrost before being applied. "In-flight" commands
   on this channel must be captured in the snapshot.

3. EXTERNAL DEPLOYMENT CHANNELS (Pi ↔ Invoker ↔ SDK)
   ──────────────────────────────────────────────────
   These are EXCLUDED from snapshot because:
   - The protocol is designed to be idempotent
   - Channels are assumed unreliable (messages can be delayed/dropped)
   - Effects are only durable when acknowledged via Bifrost commit
   - Therefore: external channel state is implicitly captured in Bifrost appends

   On restore, the invoker will resend messages; the protocol handles duplicates.


================================================================================
SELF-LOOP CHANNEL: HOW IT WORKS
================================================================================

Architecture (from crate research):
  - Single SelfProposer per leader PP (not multiple appenders)
  - Wraps BackgroundAppender with queue capacity of 50 records
  - Batches up to 5000 records before calling append_batch_erased()
  - FIFO ordering is preserved within a single appender

"In-flight" on the self-loop channel:
  1. Commands in SelfProposer/BackgroundAppender queue (submitted, not committed)
  2. Commands batched but append_batch_erased() not complete
  3. Commands committed to Bifrost but not yet applied (committed_lsn > applied_lsn)

For a consistent snapshot, we must ensure:
  - All commands generated BEFORE the snapshot decision are included
  - The snapshot LSN reflects the state after applying those commands

SOLUTION: Deferred snapshot point (non-blocking)

  We use a two-phase approach that captures all in-flight self-loop commands:

  1. When InitiateSnapshot or first marker is received at applied_lsn = X:
     a. FLUSH the SelfProposer queue: wait for all queued commands to commit
        - This ensures commands generated before the decision are included
        - Typically completes in < 10ms under normal load
     b. Note target_lsn = committed_lsn AFTER the flush
     c. Enter SNAPSHOT_PENDING state for this sid
     d. GATE OUTBOUND messages: queue but do not send cross-partition messages
        - This enforces the marker-before-messages rule
        - Incoming command processing continues (reading from own log)

  2. When applied_lsn catches up to target_lsn (typically very fast):
     - Take RocksDB checkpoint at this point
     - Now applied_lsn == target_lsn: no in-flight commands on self-loop

  3. Send markers to ALL other partitions FIRST, then:
     - Release the outbound message gate (resume sending cross-partition messages)
     - Exit SNAPSHOT_PENDING state

  Why this works:
  - Phase 1a ensures queued commands are committed before target_lsn is set
  - Phase 1d enforces CL's marker-before-messages rule
  - The apply loop constantly catches up to committed_lsn
  - The gap is typically milliseconds (just Bifrost append + apply latency)

  Bound on delay:
  - Could add a time limit (e.g., 100ms max) as a safety bound
  - In practice, the delay is negligible under normal load

  SIMPLIFICATION: One snapshot at a time
  - While in SNAPSHOT_PENDING state, ignore InitiateSnapshot and markers for
    OTHER snapshot IDs (different sids)
  - This avoids complexity of managing concurrent snapshot states
  - The brief window (milliseconds) makes this acceptable

  COORDINATOR CONSTRAINT: The coordinator MUST NOT issue concurrent snapshot
  requests. This is a system-level constraint that ensures:
  - Only one snapshot ID is active at any time across the cluster
  - If a partition rejects a snapshot request (busy with another), the
    coordinator waits for the current snapshot to complete before retrying
  - This differs from classical CL which allows concurrent snapshots per sid,
    but simplifies our implementation significantly


================================================================================
CHANDY-LAMPORT PREREQUISITES AND OUR ADAPTATIONS
================================================================================

The Chandy-Lamport algorithm requires:

1. FIFO CHANNELS
   ─────────────
   Chandy-Lamport requires FIFO ordering between each sender-receiver pair.

   CROSS-PARTITION CHANNELS:
   - Each partition Pi has its own Bifrost log (Log-Pi)
   - All messages TO Pi flow through Log-Pi
   - Bifrost provides total ordering within a log (LSN ordering)
   - Messages from sender Pj to Pi are ordered by their LSN in Log-Pi

   FIFO GUARANTEE: For any sender Pj sending to Pi, if Pj sends M1 before M2,
   then M1 appears at a lower LSN than M2 in Log-Pi. This is because:
   - Pj's shuffle enqueues messages sequentially
   - Bifrost assigns LSNs in append order
   - Pi processes Log-Pi in LSN order

   Therefore: The channel Pj→Pi (modeled as the subset of Log-Pi containing
   messages from Pj) is FIFO.

   SELF-LOOP CHANNEL:
   - Single SelfProposer per leader ensures FIFO within a PP
   - Commands are proposed sequentially with monotonic Epoch Sequence Numbers
   - BackgroundAppender preserves order within batches

2. MARKER PROPAGATION RULE (CL requirement: chandy-lamport.md:29,35)
   ─────────────────────────────────────────────────────────────────
   When a process first records its snapshot (either by initiating or receiving
   first marker), it MUST send markers on ALL outgoing channels BEFORE sending
   any further regular messages on those channels.

   This includes ALL outbound messages: cross-partition invocations, acks, etc.

   In our system:
   - On InitiateSnapshot or first SnapshotMarker received:
     1. GATE outbound messages (queue but do not send)
     2. Flush SelfProposer queue, wait for applied_lsn == target_lsn
     3. Take local snapshot
     4. For each other partition Pj: enqueue SnapshotMarker to Log-Pj
     5. RELEASE the gate (resume sending queued cross-partition messages)
     6. Resume normal processing

   The gate ensures no application messages (including OutboxProcessedAck) are
   sent after the snapshot but before the markers, preserving CL invariants.

3. CHANNEL STATE RECORDING (Classical Chandy-Lamport)
   ───────────────────────────────────────────────────
   In classical CL, each process records the "channel state" for each incoming
   channel C as: all messages received on C AFTER the local snapshot but BEFORE
   receiving the marker on C.

   This channel state represents "in-flight" messages at snapshot time.

   OUR ADAPTATION (Deferred Truncation):
   ─────────────────────────────────────
   We do NOT explicitly record channel state. Instead, we achieve the same
   consistency guarantee through a different mechanism:

   - OUTBOX: Sender keeps messages until receiver acknowledges processing
   - DEDUP: Receiver tracks which messages have been processed
   - ACKS VIA BIFROST: Acknowledgments flow through the same Bifrost channel
     as markers, preserving FIFO ordering

   CONTROL MESSAGES (Excluded from Channel State):
   ────────────────────────────────────────────────
   Like markers, OutboxProcessedAck messages are CONTROL messages, not application
   messages. Per CL (chandy-lamport.md:18), markers are "distinct from application
   messages" and "not part of any channel state."

   We treat acks the same way: they are infrastructure messages that manage the
   snapshot protocol, not application payload. Therefore:
   - Markers: excluded from channel state (per CL)
   - Acks: excluded from channel state (same reasoning)

   This means:
   - If a message M is "in-flight" at snapshot time, it's in sender's outbox
   - The channel state that CL would record is implicitly captured in the
     sender's outbox (which is part of the sender's local snapshot)
   - Acks in flight do not need to be recorded as channel state

   See "CONNECTION TO CHANDY-LAMPORT INVARIANTS" below for formal justification.

================================================================================
PHASE 1: COORDINATOR INITIATES SNAPSHOT
================================================================================

Step 1.1: Coordinator decides to take snapshot "snap-001"
────────────────────────────────────────────────────────

Coordinator appends to Log-P0:
  Command::InitiateSnapshot { snapshot_id: "snap-001" }

Log-P0 state:
  LSN 50: ... (previous commands)
  LSN 51: InitiateSnapshot { snapshot_id: "snap-001" }  ← NEW


================================================================================
PHASE 2: INITIATOR (P0) PROCESSES InitiateSnapshot
================================================================================

Step 2.1: P0 reads InitiateSnapshot from its log
────────────────────────────────────────────────

P0's partition processor reads LSN 51.

Step 2.2: P0 takes local snapshot (non-blocking)
────────────────────────────────────────────────

P0 executes:
  1. GATE outbound messages: queue but do not send cross-partition messages
     - This enforces marker-before-messages rule
  2. FLUSH SelfProposer queue: wait for all queued commands to commit
  3. Note target_lsn = committed_lsn (after flush)
  4. WAIT for applied_lsn to catch up to target_lsn
     - This happens naturally as the apply loop processes Bifrost records
     - Typically completes within milliseconds
  5. When applied_lsn == target_lsn (self-loop channel is empty):
     - FLUSH any pending writes to RocksDB
     - CREATE RocksDB checkpoint at this point
     - Snapshot captures: svc-A state, Outbox with Msg-X (seq=5)
  6. RECORD: snapshot_lsn = applied_lsn

Note: Processing continues during step 3, but any NEW commands generated
go to LSNs beyond target_lsn and are not part of this snapshot.

P0's snapshot state:
  ┌─────────────────────────────────────────────────┐
  │ Snapshot "snap-001" for P0:                     │
  │   - RocksDB checkpoint at LSN 51                │
  │   - Contains: svc-A data, Outbox[Msg-X, seq=5]  │
  │   - Dedup state at this moment                  │
  └─────────────────────────────────────────────────┘

Step 2.3: P0 sends SnapshotMarker to ALL other partitions
─────────────────────────────────────────────────────────

CRITICAL (Marker Propagation Rule): Before resuming any application processing,
P0 MUST send markers on ALL outgoing channels. In the 2-partition case, this
means sending a marker to P1. In the N-partition case, P0 would send markers
to P1, P2, ..., P(N-1).

P0's shuffle appends to Log-P1:
  Command::SnapshotMarker { snapshot_id: "snap-001", from: P0 }

Log-P1 state:
  LSN 30: ... (previous commands)
  LSN 31: (Msg-X from P0, not yet processed)  ← In-flight message
  LSN 32: SnapshotMarker { snapshot_id: "snap-001", from: P0 }  ← NEW

Step 2.4: P0 records it has sent marker to P1
─────────────────────────────────────────────

P0 tracking state:
  snap-001: {
    local_snapshot_taken: true,
    markers_sent_to: [P1],
    markers_received_from: [],      // Waiting for P1's marker
    expected_markers: [P1],
  }

Step 2.5: P0 resumes processing
───────────────────────────────

P0 continues processing commands from LSN 52 onwards.


================================================================================
PHASE 3: P1 RECEIVES MARKER (First marker triggers snapshot)
================================================================================

Step 3.1: P1 processes in-flight Msg-X at LSN 31
────────────────────────────────────────────────

Before seeing the marker, P1 processes Msg-X from P0:
  1. Check dedup: (P0, seq=5) not seen → process it
  2. Execute business logic for Msg-X
  3. Update dedup: {(P0, seq=4): done, (P0, seq=5): done}
  4. SEND ACK via Bifrost: Shuffle appends to Log-P0:
     Command::OutboxProcessedAck { source: P1, from_partition: P0, up_to_seq: 5 }

Log-P0 state:
  LSN 51: InitiateSnapshot
  LSN 52: OutboxProcessedAck { source: P1, from_partition: P0, up_to_seq: 5 }  ← NEW

CHANNEL STATE NOTE (Classical CL): In classical Chandy-Lamport, P1 records
"channel state" for channel P0→P1 as: messages received AFTER P1's snapshot
but BEFORE receiving the marker from P0.

In this case, P1's snapshot is triggered BY the marker from P0 (first marker).
Per CL rules (chandy-lamport.md:34): when the first marker arrives, channel
state for that channel is recorded as EMPTY.

Msg-X was processed by P1 BEFORE the marker arrived (LSN 31 < LSN 32), so
Msg-X is part of P1's LOCAL STATE (in dedup), NOT channel state.

In our adaptation: Msg-X is captured in P1's dedup table. Additionally, until
P0 processes the ack, Msg-X remains in P0's outbox - providing redundancy.

Step 3.2: P1 reads SnapshotMarker at LSN 32
───────────────────────────────────────────

P1 sees: SnapshotMarker { snapshot_id: "snap-001", from: P0 }

This is the FIRST marker P1 has seen for snap-001.

Step 3.3: P1 takes local snapshot (non-blocking)
────────────────────────────────────────────────

P1 executes:
  1. GATE outbound messages: queue but do not send cross-partition messages
     - This enforces marker-before-messages rule
     - The ack for Msg-X (if not yet sent) is queued, not sent
  2. FLUSH SelfProposer queue: wait for all queued commands to commit
     - This includes any commands generated while processing Msg-X
  3. Note target_lsn = committed_lsn (after flush)
  4. WAIT for applied_lsn to catch up to target_lsn
     - Typically completes within milliseconds
  5. When applied_lsn == target_lsn (self-loop channel is empty):
     - FLUSH any pending writes to RocksDB
     - CREATE RocksDB checkpoint at this point
     - Snapshot captures: svc-B state, dedup with seq=5 from P0, Outbox with Msg-Y
  6. RECORD: snapshot_lsn = applied_lsn

P1's snapshot state:
  ┌──────────────────────────────────────────────────────┐
  │ Snapshot "snap-001" for P1:                          │
  │   - RocksDB checkpoint at LSN 32                     │
  │   - Contains: svc-B data                             │
  │   - Dedup: {(P0, seq=4), (P0, seq=5)}  ← Msg-X here! │
  │   - Outbox: [Msg-Y to P0, seq=3]                     │
  └──────────────────────────────────────────────────────┘

Step 3.4: P1 sends SnapshotMarker to ALL other partitions
─────────────────────────────────────────────────────────

CRITICAL (Marker Propagation Rule): P1 must send markers to all other partitions
BEFORE resuming processing.

P1's shuffle appends to Log-P0:
  Command::SnapshotMarker { snapshot_id: "snap-001", from: P1 }

Log-P0 state:
  LSN 51: InitiateSnapshot
  LSN 52: OutboxProcessedAck { source: P1, from_partition: P0, up_to_seq: 5 }
  LSN 53: SnapshotMarker { snapshot_id: "snap-001", from: P1 }  ← NEW

Step 3.5: P1 marks channel P0→P1 as complete (no more channel state to record)
──────────────────────────────────────────────────────────────────────────────

Since the marker from P0 has arrived, P1 will not record any more messages from
P0 as "channel state" for this snapshot. (In classical CL terms: the channel
P0→P1 is now closed for this snapshot.)

P1 tracking state:
  snap-001: {
    local_snapshot_taken: true,
    markers_sent_to: [P0],
    markers_received_from: [P0],    // Got marker from P0
    expected_markers: [P0],         // All received!
    channel_state: {
      P0→P1: EMPTY   // First marker triggers snapshot; channel state is empty
    }
  }

NOTE: Msg-X is NOT channel state. It was processed BEFORE P1's snapshot, so it's
in P1's local state (dedup table). See CHANNEL STATE NOTE above for details.

Step 3.6: P1 reports snapshot complete
──────────────────────────────────────

P1 has received markers from ALL other partitions (just P0).
P1 reports to coordinator: "snap-001 complete for P1, LSN=32"


================================================================================
PHASE 4: P0 RECEIVES ACK AND MARKER
================================================================================

Step 4.1: P0 processes OutboxProcessedAck at LSN 52
───────────────────────────────────────────────────

P0 reads: OutboxProcessedAck { source: P1, from_partition: P0, up_to_seq: 5 }

P0 executes:
  1. Truncate outbox: remove all messages to P1 with seq ≤ 5
  2. Msg-X (seq=5) is removed from outbox

P0 state after truncation:
  ┌─────────────────────────────────────┐
  │ RocksDB State:                      │
  │   - Service "svc-A", key "order-1"  │
  │   - Outbox: [] ← EMPTY NOW          │
  │   - Applied LSN: 52                 │
  └─────────────────────────────────────┘

IMPORTANT: This truncation happened AFTER P0's snapshot (LSN 51).
Therefore, Msg-X IS in P0's snapshot outbox.

But wait - Msg-X is ALSO in P1's dedup (processed before P1's snapshot).

This is fine! On restore:
  - P0 will resend Msg-X (from outbox)
  - P1 will reject it (dedup shows already processed)
  - Exactly-once semantics preserved

Step 4.2: P0 processes SnapshotMarker at LSN 53
───────────────────────────────────────────────

P0 reads: SnapshotMarker { snapshot_id: "snap-001", from: P1 }

P0 already took snapshot for snap-001, so this is a subsequent marker.

P0 executes:
  1. Mark channel P1→P0 as complete for snap-001
  2. Check: have all markers been received?

CHANNEL STATE NOTE: Since P0 already snapshotted, any messages from P1 received
between P0's snapshot (LSN 51) and this marker (LSN 53) would be "channel state"
for P1→P0. In this example, no such messages exist (only the ack at LSN 52).

P0 tracking state:
  snap-001: {
    local_snapshot_taken: true,
    markers_sent_to: [P1],
    markers_received_from: [P1],    // Got marker from P1
    expected_markers: [P1],         // All received!
    channel_state: {
      P1→P0: []   // No messages received between snapshot and marker
    }
  }

Step 4.3: P0 reports snapshot complete
──────────────────────────────────────

P0 has received markers from ALL other partitions (just P1).
P0 reports to coordinator: "snap-001 complete for P0, LSN=51"

================================================================================
CONNECTION TO CHANDY-LAMPORT INVARIANTS
================================================================================

The Chandy-Lamport algorithm guarantees a CONSISTENT CUT: the recorded global
state could have existed during execution. Specifically, for any message M:

  CL INVARIANT: If M is recorded as "sent" in sender's snapshot, then either:
    (a) M is recorded as "received" in receiver's snapshot, OR
    (b) M is recorded in the channel state

Our adaptation preserves this invariant through outbox/dedup/ack-via-Bifrost:

THEOREM: For any message M from Pi to Pj, at snapshot time, M is in:
  - Pi's outbox (sender's snapshot), OR
  - Pj's dedup (receiver's snapshot), OR
  - Both

PROOF:

  Let M be a message from Pi to Pj with sequence number s.

  Case 1: Pj has NOT processed M at the time of its snapshot
  ──────────────────────────────────────────────────────────
  - M is not in Pj's dedup
  - Pj has not sent ack for M
  - Pi has not truncated M from outbox
  - Therefore: M is in Pi's outbox at Pi's snapshot time ✓

  Case 2: Pj HAS processed M at the time of its snapshot
  ──────────────────────────────────────────────────────
  - M is in Pj's dedup (captured in Pj's snapshot) ✓

  Case 3: Pj processes M AFTER Pj's snapshot (N>2 partitions only)
  ─────────────────────────────────────────────────────────────────
  NOTE: In the two-partition case, Case 3 cannot occur because Pj's snapshot
  is triggered by Pi's marker, and FIFO ordering ensures M arrives before the
  marker. However, with N>2 partitions, this case CAN occur:

  Example (3 partitions): P0 initiates, sends markers to P1 and P2.
  P1 snapshots on P0's marker. Later, P2 sends message M to P1.
  P1 processes M AFTER P1's snapshot but BEFORE P2's marker arrives.

  In classical CL, M would be recorded as "channel state" for P2→P1.

  In our adaptation, M is still captured correctly. Here's the key reasoning:

  1. Pi (the sender of M) has M in its outbox until it receives an ack
  2. The ack for M can only be sent by Pj AFTER Pj processes M
  3. Since Pj processed M after Pj's snapshot, Pj was in SNAPSHOT_PENDING
     state when it processed M (or entered that state afterward)
  4. When Pj enters SNAPSHOT_PENDING, it GATES outbound messages (including acks)
  5. Pj sends its marker to Pi BEFORE releasing the gate
  6. Therefore: the ack for M is enqueued to Pi's log AFTER Pj's marker to Pi
  7. Since Pi's log is FIFO: marker arrives at Pi before the ack
  8. Pi processes its snapshot point before or when seeing the marker
  9. Pi sees the ack AFTER its snapshot point
  10. Therefore: M is still in Pi's outbox at Pi's snapshot time ✓

  The critical invariant: because Pj gates outbound messages until its marker
  is sent, and both markers and acks travel through the same FIFO channel
  (Pi's Bifrost log), the ack cannot arrive at Pi before Pi's snapshot.

  In classical CL terms: M is "in-flight" and would be recorded as channel
  state for Pi→Pj. In our adaptation, M is captured in Pi's outbox.

  Therefore: M is always captured somewhere. ∎

WHY ACKS VIA BIFROST MATTER:
────────────────────────────
If acks were sent via network (out-of-band), this proof would fail:

  Problematic scenario:
  1. Pi sends M to Pj (M in Pi's outbox)
  2. Pi takes snapshot at LSN 51 (M in outbox ✓)
  3. Pi sends marker to Pj
  4. Pj processes M, sends ack via NETWORK (not Bifrost)
  5. Ack arrives at Pi via network, Pi truncates M from outbox
  6. Pi processes marker from Pj at LSN 53

  Now: the ack's arrival is NOT ordered with respect to the marker in Pi's log.
  The ack could "race" past the marker conceptually, causing Pi to truncate M
  before its snapshot even though Pj hadn't snapshotted yet.

By routing acks through Bifrost:
  - Acks are FIFO-ordered with markers in the receiver's log
  - If ack is at LSN < marker_lsn: Pi processes ack before snapshot
  - If ack is at LSN > marker_lsn: Pi hasn't processed ack at snapshot time
  - Either way: ordering is deterministic and matches FIFO semantics


================================================================================
WHY THIS IS CONSISTENT: CONCRETE ANALYSIS
================================================================================

Message Msg-X from P0 to P1:

  Timeline:
    1. P0 sends Msg-X (in outbox, seq=5)
    2. P0 takes snapshot ← Msg-X IN P0's snapshot (outbox)
    3. P0 sends marker to P1
    4. P1 processes Msg-X ← Msg-X now in P1's dedup
    5. P1 sends ack to P0 (via Bifrost)
    6. P1 sees marker, takes snapshot ← Msg-X IN P1's snapshot (dedup)
    7. P0 receives ack, truncates Msg-X from outbox
    8. P0 receives marker from P1

  Result: Msg-X appears in BOTH snapshots (outbox AND dedup)
  On restore: P0 resends, P1 deduplicates → exactly-once preserved ✓

Message Msg-Y from P1 to P0:

  Timeline:
    1. P1 has Msg-Y in outbox (seq=3)
    2. P0 takes snapshot (hasn't processed Msg-Y yet)
    3. P0 sends marker to P1
    4. P1 takes snapshot ← Msg-Y IN P1's snapshot (outbox)
    5. P1 sends marker to P0
    6. Eventually P0 processes Msg-Y, sends ack

  Result: Msg-Y in P1's snapshot outbox
  On restore: P1 resends, P0 processes (or deduplicates) → correct ✓


================================================================================
THE ORDERING GUARANTEE THAT MAKES IT WORK
================================================================================

Key insight: Acks flow through Bifrost (same FIFO channel as markers).

Scenario A: Ack arrives BEFORE marker in sender's log
─────────────────────────────────────────────────────
  Log-P0: [..., Ack(seq=5), ..., SnapshotMarker]
                    ↑                    ↑
                 LSN 48               LSN 51

  - P0 truncates Msg-X at LSN 48
  - P0 snapshots at LSN 51 (Msg-X already truncated)
  - But P1 must have processed Msg-X BEFORE sending ack
  - P1's marker was sent AFTER P0's marker (causality)
  - P1 snapshotted AFTER processing Msg-X (marker propagation rule)
  - Therefore: Msg-X is in P1's dedup ✓

Scenario B: Ack arrives AFTER marker in sender's log
────────────────────────────────────────────────────
  Log-P0: [..., SnapshotMarker, ..., Ack(seq=5)]
                      ↑                   ↑
                   LSN 51              LSN 55

  - P0 snapshots at LSN 51 (Msg-X still in outbox)
  - P0 truncates Msg-X at LSN 55 (after snapshot)
  - Therefore: Msg-X is in P0's outbox ✓

Either way: Message is captured somewhere. Never lost. ✓

================================================================================
WHY EXTERNAL CHANNELS (INVOKER ↔ SDK) ARE EXCLUDED
================================================================================

The PP communicates bidirectionally with external service deployments via the
invoker. Why don't we need to capture this channel state?

1. PROTOCOL IS DESIGNED FOR UNRELIABLE CHANNELS
   - The Restate ↔ SDK protocol assumes messages can be delayed or dropped
   - Every message type has retry/recovery semantics built in
   - This is fundamentally different from Bifrost (reliable, FIFO)

2. EFFECTS ARE ONLY DURABLE WHEN COMMITTED TO BIFROST
   - When the SDK sends a response (e.g., SetState, Output), the PP only
     acknowledges it AFTER the corresponding command is committed to Bifrost
   - Therefore, any "in-flight" external message that hasn't been acked is
     implicitly captured in Bifrost (the command that would process it)

3. IDEMPOTENCY HANDLES DUPLICATES ON RESTORE
   - On restore, the invoker will resend pending invocations
   - The SDK journal provides idempotent replay of side effects
   - Duplicate messages are detected and handled correctly

4. THE INVOKER STATE IS DERIVED FROM BIFROST
   - Active invocations are derived from the PP state (which is in Bifrost)
   - On restore, the invoker rescans the PP state and resumes invocations
   - No separate "invoker snapshot" is needed

THEREFORE: External channel state is implicitly captured through:
  - Bifrost commands (durable effects)
  - PP state (active invocations, journal entries)
  - Protocol idempotency (duplicate handling)

RESTORE PROCEDURE (SKETCH)
================================================================================

1. Load ClusterSnapshotMetadata for "snap-001"

2. For each partition:
   - Restore RocksDB from checkpoint
   - Bifrost log is fresh/empty (or trimmed to snapshot LSN)

3. Partition processors start:
   - P0 starts, scans outbox: finds Msg-X (seq=5)
   - P0's shuffle resends Msg-X to P1

4. P1 receives Msg-X:
   - Check dedup: (P0, seq=5) already processed!
   - Reject as duplicate
   - Send ack anyway (idempotent)

5. P0 receives ack:
   - Truncate Msg-X from outbox

6. System restored to consistent state ✓


================================================================================
SUMMARY: DEVIATION FROM CLASSICAL CHANDY-LAMPORT
================================================================================

Our implementation is a MODIFIED Chandy-Lamport that achieves the same
consistency guarantees through different mechanisms:

| Aspect                  | Classical CL              | Our Adaptation           |
|-------------------------|---------------------------|--------------------------|
| FIFO Channels           | Required                  | Provided by Bifrost LSN  |
| Marker Propagation      | Send before any messages  | Same (enforced)          |
| Channel State Recording | Explicit recording        | Implicit via outbox      |
| Acknowledgments         | Not part of algorithm     | Essential for truncation |
| Ack Delivery            | N/A                       | Via Bifrost (FIFO)       |
| Self-Loop Channel       | Treated as any channel    | Deferred snapshot point  |
| External Channels       | Would need recording      | Excluded (idempotent)    |
| Concurrent Snapshots    | Allowed (per sid)         | One at a time (simpler)  |

The key insight is that by:
  1. Keeping messages in sender's outbox until acked
  2. Routing acks through the same FIFO channel as markers
  3. Recording processed messages in receiver's dedup
  4. Draining the self-loop channel before taking snapshot
  5. Excluding external channels (invoker ↔ SDK) due to idempotency

We achieve the CL invariant (every message captured somewhere) without
explicitly recording channel state. The outbox + dedup effectively serve
as a distributed representation of what CL calls "channel state."

CHANNEL ACCOUNTING:
  - Cross-partition (Pi → Pj): Captured via outbox/dedup mechanism
  - Self-loop (Pi → Bifrost → Pi): Deferred snapshot point (wait for natural empty)
  - External (Pi ↔ Invoker ↔ SDK): Excluded; protocol is idempotent

REQUIRED CODE CHANGES
================================================================================

This section documents specific code changes required to implement the design.

1. ACK FOR DUPLICATE MESSAGES (CRITICAL)
   ──────────────────────────────────────
   Location: crates/worker/src/partition/mod.rs:893-898

   Current code:
     if Self::is_outdated_or_duplicate(dedup_information, transaction).await? {
         debug!("Ignoring outdated or duplicate message: {:?}", ...);
         return Ok(None);  // ← EARLY RETURN, NO ACK GENERATED
     }

   Problem: After restore, sender's outbox contains message M. Sender resends M.
   Receiver has M in dedup (processed before snapshot). Receiver rejects as
   duplicate and returns early WITHOUT sending ack. Sender never truncates M.

   Fix: Must send OutboxProcessedAck even for duplicate/outdated messages.
   The ack is idempotent - sending it multiple times causes no harm, but NOT
   sending it prevents outbox truncation.

   The corrected flow for duplicates:
     1. Check is_outdated_or_duplicate() → true
     2. Generate OutboxProcessedAck for the message
     3. Enqueue ack to sender's log via shuffle
     4. Return Ok(None) (don't process)

2. ACKS THROUGH BIFROST (NOT NETWORK)
   ───────────────────────────────────
   Location: crates/worker/src/partition/shuffle.rs

   Current: Shuffle truncates outbox when Bifrost confirms the append.
   This is UNSAFE for cluster snapshots because the message may not yet
   be processed by the receiver.

   Change: Receiver must send explicit acks through Bifrost. Sender truncates
   only when it sees the ack in its own Bifrost log.

   New command needed in crates/wal-protocol/src/lib.rs:
     Command::OutboxProcessedAck {
         from_partition: PartitionId,
         up_to_seq: MessageIndex,
     }

3. SNAPSHOT MARKERS THROUGH BIFROST
   ─────────────────────────────────
   Location: crates/wal-protocol/src/lib.rs

   New commands:
     Command::InitiateSnapshot { snapshot_id: ClusterSnapshotId }
     Command::SnapshotMarker { snapshot_id: ClusterSnapshotId, from: PartitionId }

   The state machine must handle these to trigger the snapshot protocol.

4. DEFERRED SNAPSHOT POINT
   ────────────────────────
   Location: crates/worker/src/partition/mod.rs (state machine)

   When taking a snapshot, must wait for applied_lsn to catch up to committed_lsn
   to drain the self-loop channel. This should be non-blocking (poll periodically
   rather than stalling processing).
