# Cluster-Wide Backup via Chandy-Lamport Distributed Snapshots

## Overview

This document describes the design for consistent cluster-wide snapshots using a
Chandy-Lamport based distributed snapshot protocol. These snapshots enable
point-in-time recovery (PITR) without requiring Bifrost log retention.

**Key insight**: Messages flow through Bifrost, so markers and acks must also flow
through Bifrost to maintain FIFO ordering guarantees required by Chandy-Lamport.

## Design Principles

1. **Markers travel through Bifrost** (same channel as messages)
2. **Acks travel through Bifrost** (same channel as markers)
3. **Per-sender channel accounting** (Bifrost is multi-sender)
4. **Deferred snapshot point** for self-loop channel (non-blocking)
5. **External channels excluded** (idempotent protocol handles retries)
6. **One snapshot at a time** (simplicity over concurrency)

## Channel Model

Each Partition Processor participates in three types of channels:

### Cross-Partition Channels (Pi → Pj, i ≠ j)

Messages flow through Log-Pj via shuffle. Primary focus of Chandy-Lamport.

### Self-Loop Channel (Pi → Log-Pi → Pi)

Commands generated by the state machine travel through Bifrost before being applied.
This IS a channel in CL terms - "in-flight" commands must be captured.

**Solution**: Deferred snapshot point - wait for `applied_lsn == committed_lsn` before
taking the snapshot. This is non-blocking (continue processing, poll periodically).

### External Channels (Pi ↔ Invoker ↔ SDK)

**EXCLUDED** from snapshot because:
- Protocol is designed to be idempotent
- Channels are assumed unreliable (messages can be delayed/dropped)
- Effects only durable when acknowledged via Bifrost commit
- On restore, invoker resends; protocol handles duplicates

## Why Coordinator-Injected Markers Don't Work

```
Problematic scenario:

1. A sends M to B (via Log B)
2. Coordinator injects marker into Log B at LSN 40
3. M arrives in Log B at LSN 50 (AFTER marker)
4. B sees marker, snapshots - M NOT in dedup
5. B processes M, sends ack to A via network (out-of-band!)
6. A receives ack, appends TruncateOutbox to Log A at LSN 99
7. Coordinator injects marker into Log A at LSN 100
8. A truncates M, then snapshots - M NOT in outbox

Result: M lost from both snapshots
```

**Root cause**: No happens-before relationship between:
- Markers in different logs
- Messages flowing A→B
- Acks flowing B→A (via network)

## Corrected Design

### Core Requirements Mapping

| CL Requirement | Implementation |
|----------------|----------------|
| FIFO channels | Bifrost log per partition, per-sender ordering within log |
| Markers on same channel | Shuffle sends SnapshotMarker to target logs |
| Acks on same channel | ProcessedAck sent via Bifrost to source's log |
| First marker triggers snapshot | PP snapshots on first marker from ANY sender |
| Channel state recording | Implicit via outbox (deferred truncation) |
| Self-loop channel | Deferred snapshot point (wait for drain) |
| External channels | Excluded (idempotent protocol) |

### Protocol Flow

```
Phase 1: Initiation
═══════════════════
Coordinator → Log P0: InitiateSnapshot(snap-001)

Phase 2: Initiator Handles InitiateSnapshot
═══════════════════════════════════════════
P0 sees InitiateSnapshot:
  1. GATE outbound messages (queue but do not send)
  2. Enter SNAPSHOT_PENDING state
  3. FLUSH SelfProposer queue (wait for all queued commands to commit)
  4. Note target_lsn = committed_lsn (after flush)
  5. When applied_lsn == target_lsn (self-loop drained):
     a. Record local state (RocksDB snapshot at this LSN)
     b. For each other partition Pi:
        - Shuffle appends SnapshotMarker(snap-001, from=P0) to Log Pi
     c. RELEASE the gate (resume sending)

Phase 3: Receiver Handles First Marker
══════════════════════════════════════
P1 sees SnapshotMarker(snap-001, from=P0) - first marker for this snapshot:
  1. GATE outbound messages
  2. Enter SNAPSHOT_PENDING state
  3. FLUSH SelfProposer queue
  4. Note target_lsn = committed_lsn (after flush)
  5. When applied_lsn == target_lsn:
     a. Record local state
     b. Mark channel P0→P1 as EMPTY (first marker triggers snapshot)
     c. For each other partition Pj (j ≠ 0, j ≠ 1):
        - Shuffle appends SnapshotMarker(snap-001, from=P1) to Log Pj
     d. RELEASE the gate

Phase 4: Receiver Handles Subsequent Markers
════════════════════════════════════════════
P1 sees SnapshotMarker(snap-001, from=P2) - already snapshotted:
  1. Channel P2→P1 state = messages from P2 after P1's snapshot but before marker
  2. (With deferred truncation: this state is in P2's outbox)
  3. Mark channel P2→P1 as complete

Phase 5: Completion
═══════════════════
When partition has received markers from ALL other partitions:
  - Report snapshot complete to coordinator
  - Exit SNAPSHOT_PENDING state
```

### Acks Through Bifrost

**Critical change**: ProcessedAck must flow through Bifrost, not network.

```
Legacy (broken):
  B processes M → shuffle gets Bifrost ack → shuffle truncates immediately

Corrected:
  B processes M → B's shuffle appends ProcessedAck to Log A → A sees ack, truncates
```

This ensures:
- Acks are FIFO-ordered with markers in the sender's log
- If A's marker is at LSN 100 and ack arrives at LSN 99: truncation "before" snapshot
- If A's marker is at LSN 100 and ack arrives at LSN 101: message in outbox at snapshot

### Acks as Control Messages

Like markers, `OutboxProcessedAck` messages are CONTROL messages, not application
messages. Per CL, markers are "distinct from application messages" and "not part of
any channel state." Acks receive the same treatment:

- Acks are infrastructure messages for the snapshot protocol
- Acks are NOT recorded as channel state
- This is consistent with CL's treatment of markers

### Per-Sender Channel Accounting

Bifrost logs are multi-sender. CL assumes one sender per channel. We model this as:

```
Log B contains messages from: P0, P1, P2, ...

For snapshot consistency, B tracks per-sender:
  - Has B received marker from P0? → Channel P0→B complete
  - Has B received marker from P1? → Channel P1→B complete
  - etc.

Channel state P_i→B = messages from P_i received after B's snapshot
                       but before marker from P_i
```

With deferred truncation + acks through Bifrost:
- Channel state is implicitly in sender's outbox
- No explicit recording needed

### One Snapshot at a Time

To keep the implementation simple, we allow only one snapshot in progress:

- While in SNAPSHOT_PENDING state, ignore new InitiateSnapshot commands
- Ignore SnapshotMarkers for different snapshot IDs
- This avoids complex multi-snapshot tracking
- Liveness: snapshot completes in bounded time (all partitions reachable)

**Coordinator Constraint**: The coordinator MUST NOT issue concurrent snapshot requests.
This is enforced at the coordinator level - it waits for one snapshot to complete before
starting another.

## Consistency Guarantee

With markers and acks through Bifrost:

```
For any message M from A to B:

AT SNAPSHOT TIME:
- M is in A's outbox (ack not yet processed by A)
  → Captured in A's snapshot
- OR M is in B's dedup (processed by B)
  → Captured in B's snapshot

NEVER lost because:
- If B processed M, B sent ack to A via Bifrost
- Ack is FIFO-ordered with A's marker
- If ack before marker: A truncated before snapshot (M in B's dedup)
- If ack after marker: M still in A's outbox at snapshot

ON RESTORE:
- Bifrost is empty/fresh
- A's shuffle rescans outbox, resends unacked messages
- B receives M, checks dedup → duplicate
- B sends ack anyway (idempotent) ← CRITICAL
- A truncates M from outbox
- Exactly-once preserved
```
